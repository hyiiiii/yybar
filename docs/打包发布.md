# 打包发布

yybar 不上架 App Store，也没有 Apple Developer ID。发版用 GitHub Actions 的「发布」工作流（`.github/workflows/release.yml`）：macOS 机器打 Apple 芯片 + Intel 通用 DMG，Windows 机器打 NSIS 安装包，两个一起挂到 GitHub Releases。第一个版本 v1.0.0 于 2026-11-19 发布。

## 1. 版本号

Mac 和 Windows 用同一个版本号，发版前两边一起改：

| 文件 | 字段 |
| --- | --- |
| `yybar.xcodeproj/project.pbxproj` | `MARKETING_VERSION`（Debug、Release 各一处） |
| `windows/src-tauri/tauri.conf.json` | `version`（决定安装包文件名 `yybar_x.y.z_x64-setup.exe`） |
| `windows/package.json`、`windows/package-lock.json` | 顶层 `version` |
| `windows/src-tauri/Cargo.toml`、`windows/src-tauri/core/Cargo.toml`、`windows/src-tauri/Cargo.lock` | `yybar`、`yybar-core` 的 `version` |

## 2. Mac：DMG

「发布」工作流在 GitHub 的 macOS 机器上跑 `scripts/make_dmg.sh`。在自己的 Mac 上也能打：

```bash
scripts/make_signing_cert.sh   # 只需一次：在登录钥匙串里创建「yybar Local Code Signing」自签证书
scripts/make_dmg.sh            # 产物在 dist/yybar-<版本>.dmg
```

- `make_dmg.sh` 调用 `scripts/build_release.sh --universal`：Release 构建 arm64 + x86_64 通用二进制。内嵌的 `YYBarClaudeWatchdog` 也按 `ARCHS` 每个架构各编一份，再用 lipo 合成。构建完用自签证书签名，再用 `hdiutil` 打成带「应用程序」快捷方式的压缩 DMG。
- `scripts/build_and_install.sh` 也用 `build_release.sh` 构建和签名，但只编本机架构，然后装到 `/Applications`。
- 自签证书只在打包的这台 Mac 上受信任，在别人的电脑上等同「身份不明的开发者」；安装包也没有经过 Apple 公证。所以第一次打开会被 Gatekeeper 拦下，有两种放行方式：
  - 到「系统设置 › 隐私与安全性」点「仍要打开」；
  - 或在终端运行 `xattr -dr com.apple.quarantine /Applications/yybar.app`。
- 用固定的自签证书而不是 ad-hoc 签名，是为了让每个版本的签名身份不变：designated requirement 按证书识别，钥匙串的访问列表能认出是同一个 App。ad-hoc 签名则每个版本都是新身份（见 `docs/技术实现.md` 中签名一节）。
- 「发布」工作流的签名：在仓库 Settings › Secrets and variables › Actions 里配了 `MAC_SIGNING_CERT_P12`（证书 .p12 文件的 base64）和 `MAC_SIGNING_CERT_PASSWORD`（导出 .p12 时设的密码），就先把证书导入临时钥匙串，用它签名；没配则是 ad-hoc 签名，每个版本签名身份都不同，用户升级后 yybar 读取钥匙串（Claude Code 登录信息）时会再问一次。配置方法：在打包用的 Mac 上打开「钥匙串访问」，登录钥匙串里右键「yybar Local Code Signing」→ 导出为 .p12 并设密码，然后 `base64 -i yybar.p12 | pbcopy` 粘到 `MAC_SIGNING_CERT_P12`。v1.0.0 没配，是 ad-hoc 签名。
- 以后有了 Apple Developer 账号，可以改用 Developer ID 签名并公证（`xcodebuild archive` → `-exportArchive` 选 Developer ID → `xcrun notarytool submit` → `xcrun stapler staple`），就不会再出现 Gatekeeper 提示。

## 3. Windows：NSIS 安装包

推送 `windows/`（或 `Resources/Logos/`）下的改动后，GitHub Actions「Windows 客户端」（`.github/workflows/windows.yml`）会跑测试并打包。产物在该次运行的 Artifacts `yybar-windows-installer` 里，NSIS 安装包在 `nsis/yybar_<版本>_x64-setup.exe`，另有 `msi/`。安装包没有代码签名，首次运行时 SmartScreen 会拦一下。

```bash
gh run download <run-id> --repo hyiiiii/yybar -n yybar-windows-installer -D dist/windows
```

## 4. 发布到 GitHub Releases

1. 改版本号（第 1 节，两边一致），更新 README 和文档，合并到 main。
2. Actions →「发布」→ Run workflow，分支选 main，「本次更新内容」填这一版的更新说明（Markdown，可留空）。
3. 工作流做的事：`mac` 任务打 DMG 并检查（主程序和 watchdog 都是 arm64 + x86_64、签名校验、`hdiutil verify`）；`windows` 任务调用「Windows 客户端」工作流跑测试、打安装包；`release` 任务核对 Mac / Windows 版本号一致，然后在这次运行的提交上打 tag `v<版本号>`，创建 Release「yybar <版本号>」，附上 `yybar-<版本>.dmg` 和 `yybar_<版本>_x64-setup.exe`，说明是填的更新内容加固定的下载安装说明。tag 已存在时创建失败，不会覆盖旧版本。
4. 改了 `scripts/build_release.sh`、`scripts/make_dmg.sh` 或 `release.yml` 的 PR 会试跑 `mac` 任务（不发布），合并前就能知道 DMG 打不打得出来。

也可以手动发：在 main 上本机运行 `scripts/make_dmg.sh`，从 Windows CI 下载安装包，然后

```bash
gh release create v1.0.0 --repo hyiiiii/yybar --target main --title "yybar 1.0.0" --notes-file notes.md \
  dist/yybar-1.0.0.dmg dist/windows/nsis/yybar_1.0.0_x64-setup.exe
```

仓库目前是私有的，所以 Release 和安装包只有仓库成员能看到和下载。
